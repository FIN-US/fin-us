# Issue Creator Skill

`.github/ISSUE_TEMPLATE/*.yml`은 **웹 UI 전용**이고 `gh issue create`는 읽지 않는다.
`gh`로 만드는 이슈의 형식·분량·메타데이터는 이 스킬이 유일한 규정 지점이다.

## 분량 규칙

주 독자는 사람이 아니라 이 이슈를 받아 작업할 에이전트다.
**평서체로 쓴다**(`~한다`, `~이다`). 존댓말 종결어미를 쓰지 않는다.
**문장을 임의로 줄바꿈하지 않는다** — 마크다운이 단일 개행을 무시하고, 이슈 본문은 버전
관리 대상이 아니다. 한 문단은 한 줄로 쓴다.

- **문제 서술은 한 문단, 3문장 이내.** 여러 작업을 묶는 우산 이슈만 항목별로 나눈다.
- **`할 일`은 항목당 한 줄**로 최대 7개. `검증`은 2문장 이내.
- **코드 인용은 3줄 이내.** 파일·라인을 지목하면 충분한 것을 붙여넣지 않는다.
- 조사 과정·시도한 것·후보안 비교는 넣지 않는다. **결론과 그 근거만** 남긴다.
- 같은 사실을 문제 서술과 `할 일`에 두 번 쓰지 않는다.

## 본문 형식

```
<문제를 한 문단으로. 파일:라인으로 지목하고, 확인한 사실만 적는다>

## 할 일

- [ ] <실행 가능한 단위로>

## 검증

<무엇을 보면 해결됐다고 판단하는지 1~2줄>
```

방향 결정이 필요하면 `할 일` 위에 선택지를 **A/B 각 한 줄**로 적고 `상태: 논의 중`을 붙인다.

## 제목과 라벨

제목은 `[<접두사>] <무엇이 문제인지>` 형식이다. 접두사와 `유형:` 라벨은 짝을 이룬다.

| 접두사 | 라벨 |
| --- | --- |
| `[FIX]` | `유형: 버그` |
| `[FEAT]` | `유형: 기능` |
| `[IMPROVE]` | `유형: 개선` |
| `[REFACTOR]` | `유형: 리팩터링` |
| `[TEST]` | `유형: 테스트` |
| `[DOCS]` | `유형: 문서` |
| `[CHORE]` | `유형: 설정` |

- `우선순위: P0`~`P3`를 **반드시 하나** 단다. 판단이 서지 않으면 `P2`.
- `상태: 논의 중`·`상태: 보류`는 해당할 때만 단다.
- 담당자는 사용자가 지정하지 않았으면 `gh api user --jq .login`으로 조회한 현재 인증 계정을 쓴다.
  "요청한 사람"을 추측하지 않는다.
- `bug`·`enhancement` 라벨은 쓰지 않는다 — 옛 템플릿 잔재이고 `유형:` 라벨과 중복이다.

## 생성

**본문은 반드시 파일에 쓰고 `--body-file`로 전달한다.** 셸 이스케이프 사고와 아래 경로 변환 문제를 함께 막는다.

```bash
gh issue create -R "<OWNER>" \
  --title "<제목>" --body-file "<본문 파일 경로>" \
  --assignee "<담당자>" --label "<유형>" --label "<우선순위>"
```

> **Git Bash 경로 변환 주의.** MSYS는 `/`로 시작하는 인자를 Windows 경로로 바꾼다.
> `/api/v1/ws`가 제목에 들어가면 `C:/Program Files/Git/api/v1/ws`로 저장된다(이슈 #256 실제 사례).
> `/`로 시작하는 문자열이 인자에 들어가면 `MSYS_NO_PATHCONV=1`을 앞에 붙이거나 PowerShell로 호출한다.

`<OWNER>`는 `gh repo view --json nameWithOwner -q .nameWithOwner`로 확정한다.
생성 전 제목·본문·라벨·담당자를 보여주고 확인받는다. 확인 없이 올리지 않는다.
