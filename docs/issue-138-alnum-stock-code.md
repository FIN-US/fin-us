## 1. 조사 방법

종목마스터 `mcp-trading/data/stocks.json`은 **저장소에 커밋되어 있다**(`mcp-trading/stock-master.js:8`의 `DEFAULT_STOCKS_PATH`가 이 파일을 가리킨다). 런타임에 KIS에서 받아오는 구조가 아니므로 전수 대조가 가능했다.

- 파일: `mcp-trading/data/stocks.json` (4,353건, `[{code, name, market, aliases}]` 배열)
- 갱신 경로: `mcp-trading/scripts/update_stock_master.py` — KRX/KIS 배포 마스터(`kospi_code.mst`, `kosdaq_code.mst`)를 내려받아 재생성

## 2. 차단 범위 재확인 — 776종목 수치는 정확하다

### 2.1 전수 분류 (확인된 사실)

`mcp-trading/data/stocks.json` 4,353건 전수 대조 결과:

| 분류 | 종목 수 | 비율 |
|---|---:|---:|
| 순수 숫자 6자 (주문 가능) | 3,577 | 82.2% |
| 순수 숫자 7자 (주문 가능) | **0** | 0.0% |
| 영숫자 6자 | 312 | 7.2% |
| 영숫자 7자 (전부 `Q` 시작) | 389 | 8.9% |
| 9자 | 75 | 1.7% |
| **차단 합계** | **776** | **17.8%** |

**이슈의 776종목 / 17.8% 수치는 정확히 재현된다.** 다만 이슈의 내역 분해(`영숫자 6~7자 701` + `9자 펀드 75`)는 맞되, 그 안의 성격 분류는 부정확하다(2.2).

부수 확인: **순수 숫자 7자 종목은 마스터에 0건이다.** 즉 현재 가드의 `\d{7}` 허용 분기는 실재하는 종목을 하나도 커버하지 않는다.

길이 분포: 6자 3,889 / 7자 389 / 8자 **0** / 9자 75. 8자가 0건이라는 사실은 `backend/stock_code.py:28-40`이 `_STOCK_CODE_RE`를 `{6,9}` 단순 상한이 아니라 `(?:[0-9A-Z]{6,7}|[0-9A-Z]{9})`로 쓴 근거이며, 본 조사에서도 동일하게 재확인됐다.

## 4. KIS Open API 쪽 미확인 사항

### 4.1 저장소가 알려주는 것 (확인된 사실)

`mcp-trading/scripts/update_stock_master.py:56`:

```python
code = header[:9].strip()
```

종목마스터의 `code`는 **KIS가 배포하는 마스터 파일(`kospi_code.mst`/`kosdaq_code.mst`)의 9자 단축코드 필드를 그대로 옮긴 값**이다(`:13-26`의 `SOURCES`). 즉 `0001A0`·`Q500020`·`F70100026`은 우리가 만든 형식이 아니라 **KIS 자신이 배포하는 식별자**다.

이것은 "KIS 생태계에 영숫자 코드가 실재한다"는 근거는 되지만, **주문 API의 `PDNO`가 그 코드를 받는다는 근거는 아니다.** 마스터 배포와 주문 접수는 다른 계층이다.

또한 `parse_master_rows`(`:51-67`)는 `tail_width`(KOSPI 228 / KOSDAQ 222)만큼의 꼬리를 **잘라 버린다**. 이 꼬리의 선두에 **증권그룹구분코드**(주권 `ST`, ETF `EF`, ETN `EN`, 신주인수권증서 `SR`, 수익증권 `BC` 등)가 들어 있는 것으로 알려져 있으나, **본 조사에서는 실제 마스터 파일을 내려받아 확인하지 못했다(추정)**. 확인된다면 4.2의 설계가 크게 단순해진다.

### 4.2 미확인 — 이 이슈의 분기 조건

| 질문 | 상태 |
|---|---|
| `order-cash`의 `PDNO`가 `0001A0`·`00088K`를 수용하는가 | **미확인** |
| `PDNO`가 `Q500020`(ETN 7자)을 수용하는가 | **미확인** |
| 펀드 9자(`F…`)가 `order-cash` 대상인가, 별도 TR인가 | **미확인** (별도일 가능성이 높다고 판단하나 근거 미확보) |
| 신주인수권증서 9자(`J…`)가 `order-cash` 대상인가 | **미확인** |

**저장소 안의 어떤 코드·데이터·테스트도 이 질문들에 답하지 않는다.** 실계좌 또는 모의투자 계좌로 실제 호출해야만 확인된다. 7장이 그 절차다.

### 6.1 판정 위치 — 어디서 형식을 가를 것인가

두 안이 있다.

**안 A (권장) — 종목마스터에 상품 구분을 실어 데이터로 판정**

`update_stock_master.py`가 지금 버리는 꼬리에서 증권그룹구분코드를 뽑아 `stocks.json`에 `type` 필드로 넣는다(4.1). 그러면 주문 가능 여부를 **코드 문자열 모양이 아니라 상품 종류로** 판정할 수 있다.

- 장점: `0001A0`이 보통주인지 ETF인지 스팩인지 코드 모양으로는 절대 알 수 없다(2.2에서 이름 휴리스틱에 의존해야 했던 이유). `type`이 있으면 정확해진다. 신규 상장으로 코드 형식이 또 바뀌어도 정규식을 다시 손댈 필요가 없다.
- 장점: #73이 언급한 "마스터 생성 시 주문 불가 종목 표시" 방안과 같은 방향이다.
- 비용: `stocks.json` 스키마 변경 → `stock-master.js`, `backend/stock_code.py:_load_master_codes`, 관련 테스트 영향. 마스터 재생성 필요.
- 리스크: 꼬리 파싱이 미검증(4.1). 먼저 실제 `.mst`를 내려받아 필드 위치를 확정해야 한다.

**안 B — 판정 지점은 그대로 두고 정규식만 단계적으로 넓힘**

G1·G2·G3의 정규식을 형식별로 넓힌다. 이슈가 제안한 방식이다.

- 장점: 변경 표면이 작고 되돌리기 쉽다.
- 단점: 코드 모양으로는 상품 구분이 안 되므로, 특정 형식을 열면 그 형식의 **모든** 종목이 함께 열린다. 예를 들어 `숫자4+영문1+숫자1`을 열면 보통주 23건과 함께 ETF 237건·스팩 27건이 동시에 열린다.

> **권장**: 롤아웃 1·2단계는 안 B로 빠르게 가되, 펀드·신주인수권처럼 주문 채널이 다를 수 있는 상품을 다루는 3단계 이전에 안 A로 전환한다.

### 6.2 정책 상수의 단일화 (안 A·B 공통, 필수)

현재 정책이 `order.js`(JS)와 `stock_code.py`(Python) 두 곳에 **문자열로 복제**돼 있고, 그 결합을 주석으로만 유지하고 있다(`order.js:80-83`, `stock_code.py:50-55`). 범위를 단계적으로 넓히는 작업에서 이 구조는 특히 위험하다 — 한쪽만 넓히면 G3에서 조용히 계속 막히거나(무해), 반대로 G3만 넓히면 사용자가 60초 pending 슬롯을 잡은 뒤 `/confirm`에서 실패한다(유해).

최소한 **두 계층이 같은 정의에서 나온다는 것을 강제하는 테스트**를 먼저 넣어야 한다. 예: `backend/tests/`에서 `mcp-trading/order.js`의 패턴 리터럴을 읽어 `_ORDERABLE_STOCK_CODE_RE`와 동치인지 대조하거나, 두 계층이 같은 케이스 목록(2.2의 형식별 대표 코드)에 대해 동일한 판정을 내는지 고정한다.

### 6.3 KIS 주문 API에 넘기는 값과 TR

현재 `order.js:88-98`은 형식과 무관하게 동일한 바디를 만든다.

```
PDNO: code            // 마스터의 단축코드 그대로
ORD_DVSN: "00"|"01"   // 지정가|시장가
EXCG_ID_DVSN_CD: "SOR"
```

TR은 `order.js:33-40`의 `selectCashOrderTrId`가 `demo`/`real` × `BUY`/`SELL`로만 고른다(`VTTC0012U`/`VTTC0011U`/`TTTC0012U`/`TTTC0011U`). **상품 종류에 따른 분기는 없다.**

형식별로 필요한 것 (**전부 7장 검증 대상**):

| 형식 | 건수 | `PDNO`에 넣을 값 | TR | 상태 |
|---|---:|---|---|---|
| 신형우선주 `숫자5+K/L` | 23 | 단축코드 그대로 | 기존 주식 TR로 충분할 것으로 **추정** | 검증 필요 |
| 신규 6자 `숫자4+영문1+숫자1` | 289 | 단축코드 그대로 | 기존 주식 TR로 충분할 것으로 **추정** | 검증 필요 |
| ETN 7자 `Q…` | 389 | 단축코드 그대로 | 기존 주식 TR로 충분할 것으로 **추정**. `ORD_DVSN` 제약 여부 미확인 | 검증 필요 |
| 신주인수권 9자 `J…` | 6 | 단축코드 그대로 | 기존 주식 TR 여부 **미확인**. 호가단위·거래제도가 다름 | 검증 필요 |
| 펀드 9자 `F…` | 69 | — | **주식 주문 TR이 아닐 가능성이 높음.** 별도 엔드포인트 필요 여부 미확인 | 검증 필요 |

`EXCG_ID_DVSN_CD: "SOR"`(최선집행)이 ETN·신주인수권에도 유효한지는 별도 확인 항목이다. 유효하지 않다면 형식별로 `KRX` 등으로 바꿔야 한다.

### 6.4 회귀 테스트 처리 — 삭제 금지, 조건부화

`mcp-trading/tests/order.test.js:112-123`을 **지우면 안 된다.** 지우면 "어떤 코드가 왜 막히는가"에 대한 명세가 사라져, 이후 가드가 잘못 넓어져도 아무것도 잡히지 않는다.

권장 처리:

1. **테스트를 "형식별 판정표"로 바꾼다.** 단일 케이스(`0001A0` 거부) 대신, 2.2의 형식별 대표 코드(`005930`, `00088K`, `0001A0`, `Q500020`, `J0036221D`, `F70100026`) 각각에 대해 기대 결과(통과 / 전용 메시지 거절 / 일반 메시지 거절)를 표로 고정한다.
2. 롤아웃 단계가 올라갈 때마다 **그 표의 해당 행만** 거절→통과로 바꾼다. 나머지 행이 그대로 red 없이 유지되는 것이 "이번 단계가 의도한 범위만 열었다"는 증거가 된다.
3. `backend/tests/test_stock_code.py`의 `TestOrderableStockCodeRe`(:163-200)와 `backend/tests/test_telegram_commands.py:1213`도 같은 표를 공유하도록 맞춘다. 특히 후자는 **시세·잔고 조회 전에 끊는다**는 성질을 고정하고 있으므로, 열린 형식에 대해서는 "조회까지 진행된다"를 단언하는 케이스로 반전시켜야 한다.
4. `test_rejects_eight_char`(:189)·`test_rejects_fullwidth_digits`(:195)는 **어느 단계에서도 유지**한다. 8자는 마스터에 0건이고(2.1), 전각 숫자는 Python `\d`와 JS `\d`의 차이를 막는 가드다.

### 6.5 되돌리기 가능한 단계적 롤아웃

각 단계는 **앞 단계가 실계좌에서 무사고로 관측된 뒤에만** 진행한다. 단계마다 G1·G2·G3를 **동시에** 바꾼다(6.2).

| 단계 | 여는 대상 | 건수 | 근거 강도 | 되돌리기 |
|---|---|---:|---|---|
| **0** | (코드 변경 없음) 7장 검증 수행 | 0 | — | — |
| **1** | 신형우선주 `숫자5+[A-Z]` | 23 | 가장 높음. 명백한 지분증권이고 거래제도가 보통주와 같다 | 정규식 1줄 복원 |
| **2** | 신규 6자 `숫자4+[A-Z]숫자1` | 289 | 높음. 단 ETF·스팩이 섞여 있어 관측 범위가 넓다 | 정규식 1줄 복원 |
| **3** | ETN 7자 `Q숫자6` | 389 | 중간. 상품 특성상 `ORD_DVSN`·호가 제약 확인 필요 | 정규식 1줄 복원 |
| **4** | 신주인수권 9자 `J…` | 6 | 낮음. 길이 상한 확대가 필요해 변경 표면이 커진다 | 길이 상한 복원 |

단계 1~3은 길이 상한(`{6,7}`)을 건드리지 않으므로 `stock_code.py:40`의 `_STOCK_CODE_RE`나 8자 배제 로직에 영향이 없다. 단계 4부터 9자를 주문 범위에 넣으므로 **이때 처음으로 길이 상한이 바뀐다** — 이슈가 제안한 `/^[0-9A-Z]{6,9}$/`를 한 번에 적용하면 8자(마스터 0건)까지 열리므로, `(?:[0-9A-Z]{6,7}|[0-9A-Z]{9})` 형태를 써야 한다(`stock_code.py:35-38`이 같은 이유로 이미 그렇게 돼 있다).

각 단계에서 `mcp-trading/index.js:536,541`의 스키마 설명 문구("6자리 종목코드")도 함께 갱신해야 한다. *(단 이 조사 시점에 `index.js`는 다른 작업이 진행 중이므로 본 문서에서는 변경하지 않았다.)*

### 6.6 실패 시 대안

7장 검증에서 KIS가 영숫자 `PDNO`를 **거부**하면, 이슈의 서술대로 현 상태(정확한 거절)가 최선이다. 다만 그 경우에도 다음은 개선 여지가 있다.

- `backend/telegram_commands.py:790`의 문구 "ETN·펀드 등 영숫자 종목코드는 아직 주문 대상이 아닙니다"는 **부정확하다**(2.2). 차단 대상의 상당수가 보통주·우선주다. 상품군을 단정하지 않는 문구로 바꾸는 것이 맞다.
- #73이 제안한 대로 `update_stock_master.py`가 주문 불가 종목을 마스터에 표시하면, 조회 단계에서 미리 알릴 수 있다(안 A와 같은 작업).

## 7. 검증 절차 — 사람이 실행해야 하는 확인

**목적**: "KIS Open API `order-cash`가 영숫자 `PDNO`를 수용하는가"에 예/아니오로 답한다.

### 7.1 사전 준비

1. 모의투자 계좌와 모의투자 앱키를 준비한다(`openapivts.koreainvestment.com`).
2. `mcp-trading`의 환경 변수를 모의투자로 맞춘다. `order.js:43-53`의 `validateOrderEnvMatchesUrl`이 `order_env=demo`일 때 `KIS_URL`에 `openapivts`가 포함될 것을 요구한다.
   - `KIS_URL=https://openapivts.koreainvestment.com:29443`
   - `KIS_APP_KEY`, `KIS_APP_SECRET` = 모의투자용
   - `KIS_ACCOUNT_NO` = 모의계좌 8자리 + 상품코드 2자리
   - `KIS_REAL_ORDER_ENABLED`는 **설정하지 않는다** (`order.js:56-61`이 실계좌를 막는다)

### 7.2 1단계 — 조회로 코드 유효성 먼저 확인 (무위험)

주문 전에, 대상 코드가 KIS 조회 API에서 인식되는지 본다. 이건 우리 코드로 바로 된다(3.2에서 통과가 확인된 경로).

```bash
cd mcp-trading
# get_stock_quote 툴을 각 형식 대표 코드로 호출
#   00088K (신형우선주) / 0001A0 (신규 6자) / Q500020 (ETN)
#   J0036221D (신주인수권) / F70100026 (펀드)
```

- **성공 판정**: 응답의 `output.stck_prpr`(현재가)가 0이 아닌 값으로 온다.
- **의미**: 성공하면 그 코드가 KIS 시스템에서 유효한 식별자임이 확인된다. 실패하면 주문은 볼 것도 없다.
- **주의**: 조회 성공은 **주문 가능의 증거가 아니다.** 이 단계는 후보를 걸러내는 용도다.

### 7.3 2단계 — 모의투자 주문 실호출 (핵심 확인)

가드를 코드에서 풀지 말고, **가드를 우회하는 일회성 스크립트**로 확인한다. `order.js`의 `buildCashOrderBody`를 쓰지 않고 바디를 직접 만들어 `kis-client.js`로 POST한다. 이렇게 하면 저장소의 정책 코드를 건드리지 않고 답을 얻는다.

- 엔드포인트: `POST /uapi/domestic-stock/v1/trading/order-cash`
- TR: `VTTC0012U` (모의 매수)
- 바디: `order.js:88-98`과 동일한 형태에서 `PDNO`만 대상 코드로 교체

```
CANO             = 계좌 앞 8자리
ACNT_PRDT_CD     = 계좌 뒤 2자리
PDNO             = 00088K   ← 형식별로 바꿔가며 반복
ORD_DVSN         = "00"     (지정가)
ORD_QTY          = "1"
ORD_UNPR         = 현재가보다 충분히 낮은 값   ← 체결되지 않게
EXCG_ID_DVSN_CD  = "SOR"
SLL_TYPE         = ""
CNDT_PRIC        = ""
```

> **체결 방지**: 매수는 현재가보다 **훨씬 낮은** 지정가로 낸다. 접수만 되고 체결되지 않으므로 되돌리기가 쉽다. **시장가(`ORD_DVSN: "01"`)로 시험하지 말 것.**

### 7.4 성공/실패 판별

응답의 `rt_cd`, `msg_cd`, `msg1`을 본다.

| 응답 | 해석 | 다음 |
|---|---|---|
| `rt_cd == "0"` + `output.ODNO`(주문번호)가 채워짐 | **수용.** 그 형식은 `order-cash`로 주문된다 | 6.5의 해당 단계 진행 |
| `rt_cd != "0"` + `msg1`이 **종목코드/상품 자체를 문제 삼음** (예: 종목코드 오류, 취급 불가 상품) | **거부.** 그 형식은 열면 안 된다 | 6.6으로 |
| `rt_cd != "0"` + `msg1`이 **주문 조건을 문제 삼음** (예: 증거금 부족, 호가단위 오류, 장 미개장, 모의투자 미지원 종목) | **판정 불가.** 코드 형식 문제가 아니다 | 조건을 고쳐 재시도. 특히 "모의투자 미지원"이면 7.5로 |

- **반드시 각 형식을 개별로 판정한다.** 5개 대표 코드가 서로 다른 답을 낼 수 있다. 하나 성공했다고 나머지를 유추하지 말 것.
- **반드시 대조군을 같이 돌린다.** 같은 스크립트로 `005930`(삼성전자)을 먼저 주문해 `rt_cd == "0"`이 나오는지 확인한다. 대조군이 실패하면 계좌·환경 설정 문제이지 종목코드 문제가 아니다.
- 접수된 주문은 확인 후 취소한다. 미체결 주문은 `get_today_daily_orders`(`index.js:441`)로 조회할 수 있다.

### 7.5 모의투자에서 판정이 안 나올 경우

모의투자는 취급 종목이 제한될 수 있다(4.2, 미확인). 대조군 `005930`은 성공하는데 대상 코드만 "모의투자 미지원" 계열로 실패한다면, 모의투자로는 이 질문에 답할 수 없다.

그때의 대안:
1. 실계좌 + `KIS_REAL_ORDER_ENABLED=true`로, **1주 / 현재가보다 훨씬 낮은 지정가**로 접수만 시킨 뒤 즉시 취소한다. 체결 위험은 낮지만 0은 아니다. 시장가 금지.
2. 또는 KIS 고객지원에 문의해 서면 근거를 받는다 — 실거래 위험이 없는 유일한 경로다.
