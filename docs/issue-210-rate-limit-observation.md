> 기준 커밋: `7bdf73a` (origin/main) + 이 PR
> 작성일: 2026-09-06

## 0. 한눈에 보기

| 항목 | 상태 |
|---|---|
| KIS 유량 제한 오류코드가 존재한다 (`EGW00201` "초당 거래건수 초과") | **공식 문서로 확인** (koreainvestment/open-trading-api README) |
| 모의투자 계좌의 호출 제한이 실전보다 낮다 | **공식 문서로 확인 — 단, 정성적 서술뿐** (`mcp-trading/index.js` 상단 조사 주석) |
| 실전 "표준 20 TPS" | **반공식** — 언론 보도에서만 확인, 원문 미인용 |
| 실제 임계치(초당 몇 회) | **미확인. 실계좌 없이 확인 불가** |
| 페이지당 지연(ms) | **미확인** |
| 제한 단위가 계좌인가 앱키인가 TR인가 | **미확인** (PR #264 리뷰가 제기한 계좌 단위 가설) |
| 90초/15초 예산의 근거 | **없음.** `index.js`의 예산 주석이 "측정치가 없어"라고 직접 밝힌다 |

**결론: 지금 필요한 것은 코드가 아니라 측정이다.** 유량 제어(토큰 버킷·백오프·재시도)를
설계하려면 임계치를 알아야 하는데, 토큰 버킷의 크기를 정하는 데 필요한 숫자가 바로 그
미확인 값이다. 그래서 이 PR은 제어를 만들지 않고 **측정을 가능하게만** 만들었다.
아래 절차는 사람이 실계좌에서 실행해야 한다.

## 1. 왜 사람이 실행해야 하는가

- KIS는 유량 제한 수치를 공개하지 않는다. 임계치는 실제로 쳐 보고 `EGW00201`이 돌아오는
  지점을 찾는 수밖에 없다.
- 모의투자 계좌로 재면 **숫자가 이전되지 않는다**. `mcp-trading/index.js` 상단 조사 주석이
  기록하듯 공식 README가 "모의투자 계좌는 REST API 호출 제한이 낮으니 연속 호출이 많으면
  실전투자 계좌를 권장"한다고 명시한다. 모의에서 나온 임계치를 실전 기본값으로 넣으면
  불필요하게 느려지고, 반대 방향의 오해도 만든다(3장 참조).
- 자동화된 부하 테스트로 대신할 수 없다. 유량 제한을 일부러 때리는 스크립트는 실계좌
  자격증명으로 실제 주문 API 게이트웨이를 두드리는 일이라 사람의 판단이 있어야 한다.

## 2. 무엇을 켜는가

루트 `.env`에 한 줄을 넣고 재배포한다.

```
KIS_REQUEST_LOG=1
```

- 별칭 `FINUS_KIS_REQUEST_LOG`도 같다. `KIS_` 쪽을 먼저 읽는다
  (`mcp-trading/balance.js`의 `readPageDelayMsEnv`와 같은 관례).
- `1`/`true`/`yes`/`on`이면 켜짐, `0`/`false`/`no`/`off`면 꺼짐. 그 밖의 값은 stderr에
  경고를 남기고 기본값(off)으로 돌아간다.
- **끄더라도 유량 제한 판정 줄(`class=rate_limit`)은 항상 나간다.** 게이트가 막는 것은
  정상 요청의 타이밍 줄뿐이다 — 연속조회 1회가 최대 50페이지이고 그런 도구가 셋이라
  상시로 켜면 로그가 잠긴다.
- 측정이 끝나면 다시 끈다.

### 로그 줄의 모양

KIS 요청 1건마다 stderr에 정확히 한 줄이 나간다.

```
[kis-req] ts=2026-09-06T09:00:42.124Z pid=33124 tr_id=TTTC0081R elapsed_ms=3 http=200 rt_cd=0 msg_cd=MCA00000 class=ok msg1="정상처리 되었습니다."
[kis-req] ts=2026-09-06T09:00:42.126Z pid=33124 tr_id=TTTC0081R elapsed_ms=1 http=200 rt_cd=1 msg_cd=EGW00201 class=rate_limit msg1="초당 거래건수를 초과하였습니다. 계좌 ********"
```

| 필드 | 뜻 |
|---|---|
| `ts` | 요청 완료 시각(ISO 8601, UTC) |
| `pid` | mcp-trading 프로세스 id. **프로세스 구분이 이 측정의 핵심이다**(5.3) |
| `tr_id` | 어느 TR인가 (`TTTC0081R` 일별체결, `TTTC8434R` 잔고, `TTTC8494R` 실현손익 등). 토큰 발급은 TR이 아니라 `tokenP`로 찍힌다 |
| `elapsed_ms` | 요청 1건 소요 시간. **페이지당 지연이 여기서 나온다**(5.2) |
| `http` | HTTP 상태. 유량 제한은 200 + `rt_cd=1`로 오는 경우가 있어 이것만 보면 안 된다 |
| `rt_cd` | KIS 응답 코드. `0`이 정상 |
| `msg_cd` | KIS 오류코드. `EGW00201`/`EGW00133`이 유량 제한 |
| `class` | `ok` / `rate_limit` / `other` |
| `err` | 전송 실패 시 axios 에러 코드(`ECONNABORTED` = 8초 타임아웃 등). 성공하면 없음 |
| `msg1` | KIS 한국어 메시지. 8자리 이상 연속 숫자는 `*`로 가려서 나간다 |

### 어디가 계측되고 어디가 안 되는가

계측 지점은 두 곳이다.

| 경로 | `tr_id` | 계측 |
|---|---|---|
| `index.js`의 `kisApiGet` — 여섯 개 **조회(GET)** 경로가 전부 여기를 지난다(연속조회 두 루프 + `get_balance` + 단건 조회들) | 실제 TR ID | ✅ |
| `index.js`의 `getAccessToken` — `POST /oauth2/tokenP` | `tokenP` | ✅ |
| `kis-client.js:16` — hashkey `POST` | — | ❌ **안 나온다** |
| `kis-client.js:114` — 주문 `POST` | — | ❌ **안 나온다** |

- 5.3의 계좌 단위 가설을 보려면 단건 조회들이 함께 찍혀야 하는데, `kisApiGet` 한 곳이
  그것을 전부 덮는다.
- 토큰 발급 성공 줄은 `rt_cd=-  msg_cd=-`로 나온다. 토큰 응답 바디에 그 필드가 없기
  때문이며 정상이다(`access_token`은 포맷터가 읽지 않으므로 줄에 실리지 않는다).
  실제 모양: `[kis-req] ts=... pid=... tr_id=tokenP elapsed_ms=14 http=200 rt_cd=- msg_cd=- class=ok`
- **토큰 발급이 5.3에서 특히 중요하다.** mcp-trading은 도구 호출 1건마다 새로 뜨는 단명
  프로세스라(3장), 캐시가 비었거나 만료된 순간 동시에 뜬 프로세스들이 전부 `tokenP`로
  몰린다. 이것이 5.3이 보려는 프로세스 간 버스트 그 자체다. `EGW00133`이 실제로 관측될
  가능성이 있는 곳도 사실상 이 경로다.
- **주문 경로(`place_order`)의 KIS 요청 2건은 로그에 없다.** `mcp-trading/kis-client.js`가
  이 PR의 범위 밖이라 계측하지 않았다. 4장이 "주문 API로 유량 제한을 때리지 말 것"이라
  측정 대상도 아니지만, 초당 요청 수를 셀 때 **주문이 섞인 구간은 실제보다 2건 적게
  집계된다**는 것을 알고 세야 한다. 측정 중에는 주문을 넣지 않는 편이 낫다.

### 로그에 절대 안 나가는 것

`appkey`, `appsecret`, `authorization: Bearer <토큰>`, `CANO`(계좌번호), 요청 URL·params.
포맷터는 axios 에러의 `config`/`request`/`headers`/`params`/`message`를 아예 읽지 않는다
(`mcp-trading/kis-rate-limit.js`, 회귀 테스트는 `mcp-trading/tests/kis-rate-limit.test.js`의
"로그 줄에는 appkey·appsecret·Bearer 토큰·계좌번호가 절대 실리지 않는다").
`msg1`은 KIS 서버가 준 문자열이라 계좌번호가 되울려 올 수 있어 8자리 이상 숫자를 가린다.

> **다만 `[kis-req]` 줄 밖은 이 보장의 대상이 아니다.** 연속조회 2페이지 이후 실패 시
> `balance.js`가 남기는 `... 조회 실패: ${error.message}` 줄은 KIS의 `msg1`을 마스킹 없이
> 그대로 싣는다(이 PR 이전부터 그랬고, 이 PR은 그 파일을 건드리지 않았다). 수집한 로그를
> 이슈나 채팅에 붙일 때는 `[kis-req]`로 시작하는 줄만 골라 붙일 것.

## 3. 로그를 어디서 걷는가 — **Python 로깅 파이프라인에는 안 들어온다**

여기가 가장 틀리기 쉬운 지점이다.

mcp-trading은 백엔드가 **도구 호출 1건마다 새로 띄우는 단명 자식 프로세스**다
(`backend/services.py`의 `run_mcp_tool`, `finus_nat/src/nat_finus_nat/finus_api.py`가
호출마다 `stdio_client`를 새로 연다). MCP Python SDK의 `stdio_client`는 자식의 stderr를
`errlog=sys.stderr`로 잇는 것이 기본이고, 두 호출부 모두 이 인자를 넘기지 않는다 — 즉
자식의 stderr는 **부모 프로세스의 stderr 파일 디스크립터로 그대로 흘러간다.**

따라서:

- ✅ 컨테이너/서비스 로그에 남는다 → 여기서 걷는다.
- ❌ 백엔드의 Python `logging`을 거치지 않는다. 로그 레벨을 올려도 안 나오고, 애플리케이션
  로그 파일이나 구조화 로그 싱크에도 안 들어온다.
- ❌ MCP 도구 응답(JSON-RPC stdout)에도 안 들어온다. stdout은 프로토콜 채널이라
  `mcp-trading/index.js`가 `console.log`를 `console.error`로 돌려 두었다.

수집 명령:

```bash
# Docker Compose (docker-compose.yml의 backend / finus-nat 서비스)
docker compose logs -f --no-log-prefix backend | grep '^\[kis-req\]' | tee kis-req.log
docker compose logs -f --no-log-prefix finus-nat | grep '^\[kis-req\]' | tee -a kis-req.log

# systemd
journalctl -u <서비스명> -f | grep -o '\[kis-req\].*' | tee kis-req.log
```

줄이 자기 `ts`를 들고 있으므로 수집기가 시각을 붙여 주지 않아도 된다. 수집기 시각과
줄의 `ts`가 어긋나면(버퍼링) **줄의 `ts`를 믿는다.**

백엔드와 NAT이 각각 mcp-trading을 띄우므로 **두 서비스 로그를 모두 걷어야** 5.3의 겹침이
보인다. 한쪽만 보면 겹침이 없는 것처럼 보인다.

## 4. 어느 계좌에서 재는가

**실전투자 계좌(`https://openapi.koreainvestment.com:9443`)에서 잰다.**

- 모의투자(`openapivts`)는 공식 문서가 호출 제한이 **더 낮다**고 밝힌 별개 등급이다
  (`mcp-trading/index.js` 상단 조사 주석). 모의에서 나온 숫자를 실전 기본값으로 넣으면
  실전에서 불필요하게 느려진다. 반대로 "모의에서 안 걸렸으니 실전도 괜찮다"는 추론도
  성립하지 않는다 — 두 등급의 관계는 부등호 방향만 알고 비율은 모른다.
- 모의에서 먼저 도는지 확인하는 리허설은 해도 좋다. 다만 **리허설에서 나온 수치는 기록만
  하고 기본값 산정에는 쓰지 않는다.**
- 실현손익 조회(`get_balance_rlz_pl`)는 모의 계좌에서 아예 잔고 요약으로 대체되므로
  (`index.js`의 `isPaperTradingKisUrl` 분기) 모의 리허설로는 그 TR을 측정할 수 없다.
- 조회 TR만 쓴다. **주문 API(`place_order`)로 유량 제한을 때리지 말 것.**
- 장중에 잰다. 장 마감 후에는 조회가 가벼워 지연이 과소평가된다. 다만 실계좌 조회가
  거래에 영향을 주지 않는 시간대(예: 장 초반 혼잡 구간을 피한 시각)를 고르는 편이 낫다.

## 5. 무엇을 뽑아내는가 — 숫자 세 개

### 5.0 먼저 페이지 수 `P`를 센다 — 5.1이 성립하는 계좌인지 판정

**이 절을 건너뛰면 5.1이 조용히 헛돈다.** `KIS_*_PAGE_DELAY_MS`는 **한 번의 연속조회 루프
안에서 페이지와 페이지 사이**의 간격만 정한다(`balance.js`의 `fetchAllPaged`에서
`pages > 0`일 때만 대기한다). 그러니 오늘 주문 내역이 한 페이지에 다 들어오는 계좌
— 거래가 많지 않은 계정에서는 이쪽이 보통이고, 거래가 없는 날은 0페이지다 — 에서는
루프가 요청을 한 번만 내보내고 **대기값이 500이든 0이든 아무 차이가 없다.** 그 상태로
5.1의 스윕을 돌면 일곱 값 전부에서 `rate_limit` 0건이 나오고, 그것은 임계치에 대해
아무것도 말해 주지 않는다.

**방법:** 5.2의 수집을 한 번 돌려서(`KIS_REQUEST_LOG=1`, `get_today_daily_orders` 1회)
그 도구 호출이 만든 조회 요청 수를 센다. 그것이 페이지 수 `P`다.

```bash
# tokenP를 빼고(조회가 아니다) 그 한 번의 호출이 만든 조회 요청 수를 센다
grep '^\[kis-req\]' kis-req.log | grep -v 'tr_id=tokenP' | grep -c 'tr_id=TTTC0081R'
```

**판정:**

| `P` | 어떻게 하는가 |
|---|---|
| `P >= 2` | 5.1을 그대로 진행한다. 대기값이 실제로 요청 간격을 움직인다. |
| `P <= 1` | **5.1은 이 계좌에 적용되지 않는다.** 스윕을 돌리지 말고 5.3으로 간다. |

`P <= 1`일 때 5.3이 버스트 발생기 역할을 대신한다: 대기값을 내리는 대신 **동시 호출 수
`N`을 올린다**(도구 호출을 동시에 `N`개 띄운다 — 5.3의 방법 그대로). 기록도 "대기 N ms에서
초당 M건"이 아니라 **"동시 호출 `N`개에서 초당 최대 M건, `rate_limit` K건"**으로 남긴다.
`N`을 1부터 올리면서 `rate_limit`이 처음 나오는 지점을 찾는다.

이 경로는 덤이 아니라 오히려 본선에 가깝다. 5.3이 애초에 제기하는 가설이 "제한이 계좌
단위라면 루프 안의 대기는 답이 아니다"이기 때문이다 — `P <= 1`인 계좌에서는 루프 안의
대기가 답일 수 **없다는** 것이 이미 확정이다.

### 5.1 실제 TPS 임계치 (`P >= 2`인 계좌에서만)

> 먼저 5.0으로 `P`를 확인할 것. `P <= 1`이면 이 절을 건너뛰고 5.3으로 간다.


**질문:** 초당 몇 건부터 `EGW00201`/`EGW00133`이 돌아오는가.

**방법:** `KIS_DAILY_CCLD_PAGE_DELAY_MS`를 큰 값에서 작은 값으로 내리면서 연속조회를
반복 실행한다(예: `500` → `300` → `200` → `150` → `100` → `50` → `0`). 각 값에서
`get_today_daily_orders`를 여러 번 돌린다. 재배포 없이 값만 바꿔 넣을 수 있게 만들어 둔
것이 PR #340의 env다.

**뽑을 것:**

```bash
grep 'class=rate_limit' kis-req.log | wc -l          # 각 대기값에서의 유량 제한 건수
grep 'class=rate_limit' kis-req.log | head -1        # 처음 걸린 시각과 tr_id
```

`rate_limit`이 0건이 되는 가장 작은 대기값이 하한이다. 그 값에서 초당 요청 수를 세면
임계치가 나온다:

```bash
# grep -o로 뽑는다. sed 's/.*ts=...*/\1/'는 패턴이 안 맞는 줄(ts=-)을 통째로 통과시켜
# 버킷 하나를 오염시킨다.
grep -oE 'ts=[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}' kis-req.log | cut -d= -f2 \
  | sort | uniq -c | sort -rn | head    # 초 단위 버킷별 요청 수의 최댓값
```

**기록할 형식:** "대기 N ms에서 초당 최대 M건, `rate_limit` K건". N·M·K를 전부 적는다.
0건이라는 사실만으로는 임계치를 모른다 — 걸린 지점과 안 걸린 지점이 둘 다 있어야 한다.
**전 구간에서 0건이면 그것은 "임계치가 높다"가 아니라 "버스트를 못 만들었다"는 뜻이다.**
그때는 5.0의 판정으로 돌아가 `P`를 확인하고, 5.3의 동시 호출 `N`으로 버스트를 만든다.

### 5.2 페이지당 지연

**질문:** KIS 요청 1건이 실제로 몇 ms 걸리는가. 90초/15초 예산이 타당한가.

**뽑을 것:** `elapsed_ms`의 분포(중앙값·p95·최댓값)와 페이지 수.

```bash
# grep -o로 뽑는다. sed 's/.*elapsed_ms=([0-9]+).*/\1/'는 elapsed_ms=-인 줄(측정값 부재,
# kis-rate-limit.js의 ABSENT)을 매칭하지 못해 줄을 통째로 통과시키고, sort -n이 그것을
# 0으로 취급해 중앙값·p95를 아래로 끌어내린다.
grep -oE 'elapsed_ms=[0-9]+' kis-req.log | cut -d= -f2 | sort -n \
  | awk '{a[NR]=$1} END {print "n="NR, "med="a[int(NR/2)], "p95="a[int(NR*0.95)], "max="a[NR]}'
```

`err=ECONNABORTED`가 보이면 요청당 8초 타임아웃(`kisAxios`)에 걸린 것이다. 이게 나오면
타임아웃 자체를 재검토해야 하므로 별도로 센다.

**기록할 형식:** "페이지당 중앙값 X ms, p95 Y ms, 최대 Z ms, 실제 페이지 수 P".
여기서 나온 `P`가 5.0의 판정 입력이다.

### 5.3 계좌 단위 가설 — 별개 프로세스의 호출이 서로를 밀어내는가

**질문:** PR #264 리뷰가 제기한 것. 제한이 **계좌 단위**라면, 페이지 간 대기를 아무리 늘려도
소용이 없다 — `get_today_daily_orders`, `get_balance_rlz_pl`, 백엔드의 `get_balance`는
서로 다른 프로세스에서 도는 서로 다른 호출 경로라 루프 안의 대기가 서로를 볼 수 없다.

**방법:** 세 도구를 **동시에** 호출한다(백엔드 API를 세 창에서 동시에 치거나, NAT 일지
에이전트가 도는 시각에 맞춰 잔고 조회를 겹친다).

**뽑을 것:** `pid`가 다른 줄들의 `ts`가 겹치는 구간에서 `rate_limit`이 나는가.

```bash
grep '^\[kis-req\]' kis-req.log | sort -t= -k2 \
  | sed -E 's/.*ts=([^ ]+) pid=([0-9]+) tr_id=([^ ]+).*class=([a-z_]+).*/\1 \2 \3 \4/'
```

- 서로 다른 `pid`의 요청이 같은 초 안에 있고 그 중 하나가 `rate_limit`이면 **계좌(또는
  앱키) 단위 가설이 지지된다.** 이때는 페이지 간 대기가 답이 아니고, 프로세스를 가로지르는
  게이트(파일 락 기반 토큰 버킷 등 — 토큰 캐시가 이미 쓰는 방식)가 필요하다.
- 겹쳤는데도 `rate_limit`이 없고 단일 프로세스 고속 반복에서만 나면 **연결/프로세스 단위**로
  볼 근거가 생기고, 페이지 간 대기만으로 충분하다.
- **판정 불가도 결론이다.** 겹침 자체를 못 만들었으면 "미확인"으로 적는다.

## 6. 숫자를 어디에 되먹이는가

| 얻은 숫자 | 반영할 곳 | 방법 |
|---|---|---|
| TPS 임계치 (5.1) | `KIS_DAILY_CCLD_PAGE_DELAY_MS`, `KIS_BALANCE_RLZ_PL_PAGE_DELAY_MS` | 먼저 `.env`로 넣어 운영에서 확인한 뒤, 확정되면 `index.js`의 기본값 `0`을 그 값으로 바꾸고 근거를 주석에 남긴다 |
| 페이지당 지연 (5.2) | `DAILY_CCLD_TIME_BUDGET_MS` / `BALANCE_RLZ_PL_TIME_BUDGET_MS` (90초), `BALANCE_TIME_BUDGET_MS` (15초) | `페이지당 p95 × 실제 페이지 수 + 대기 × (페이지 수 - 1)`이 예산 안에 드는지 본다. 남으면 줄이고, 넘치면 상위 하드컷(`run_mcp_tool` 30초, `diary_agent.yml` 120초)부터 다시 본다 |
| 실제 페이지 수 (5.2) | `DAILY_CCLD_MAX_PAGES` / `BALANCE_RLZ_PL_MAX_PAGES` (50), `BALANCE_MAX_PAGES` (20) | 실제 최댓값의 몇 배인지 확인. 상한이 실제 페이지 수와 비슷하면 데이터가 조용히 잘리고 있다는 뜻이다 |
| 계좌 단위 여부 (5.3) | 설계 결정 | 계좌 단위로 확인되면 페이지 간 대기는 부분 해법일 뿐이다. 그때 비로소 프로세스 간 게이트를 설계한다 — **그전에는 만들지 않는다.** 크기를 정할 숫자가 없기 때문이다 |

되먹일 때 지켜야 할 것:

1. **대기값은 그 루프의 시간 예산보다 작아야 한다.** 예산 이상이면 첫 페이지 직후 예산이
   소진되어 연속조회가 항상 1페이지로 잘린다. 파서가 이 경우 경고를 남기고 기본값으로
   되돌린다(`balance.js`의 `readPageDelayMsEnv`).
2. **기본값을 바꾸는 커밋에는 측정 데이터를 함께 남긴다.** 지금 90초/15초에 근거가 없는
   이유가 바로 그것이 빠졌기 때문이다.
3. `fetchAllBalance`(잔고 조회)에는 여전히 대기를 넣지 않는다 — PR #200이 정한
   "관측 가능한 동작 불변" 전제 때문이다. 바꾸려면 별도 결정이 필요하다.
