# NFR-05 — 외부 LLM 호출 시 개인·계좌 정보 비식별화

관련 요구사항: F-17(비식별화). 이 문서는 F-17/NFR-05 관련 작업이 진행되며 갱신된다.
레포 전체를 조사했으나 이 요구사항을 기록한 기존 문서를 찾지 못해(#230 착수 시 확인)
이 파일을 새로 만들어 갱신한다.

## 범위

외부 LLM 제공자(OpenAI/Anthropic/Ollama/NAT)로 나가는 프롬프트에서 다음 3종을 마스킹한다.

| 대상 | 비고 |
| --- | --- |
| 한국 계좌번호 | `KIS_ACCOUNT_NO` 형식: CANO(8자리) + 상품코드(2자리), 하이픈 유무 무관 |
| 원화 금액 | `1,234,567원` / `1234567원` / `123만원` / (라벨 컨텍스트에서) `1234567` |
| 보유 수량 | 잔고 리포트의 `hldg_qty` 유래 값(`N주`) |

## 적용 경로 — 해소됨 (#230)

`backend/services.py`의 `llm_chat()`이 OpenAI/Anthropic/Ollama/NAT 4개 provider 경로의
단일 진입점이다. `backend/pii_mask.py`의 `mask_pii()`/`unmask_pii()`를 이 함수 안에서
호출해, `llm_chat()`을 거치는 모든 프롬프트가 자동으로 마스킹된다.

- `perform_stock_analysis`의 `_build_nat_prompt`/`_build_toolless_prompt` 경로
- `generate_morning_briefing`이 조립하는 모닝 브리핑 프롬프트 — KIS 잔고 리포트
  텍스트(`get_balance` 결과)를 backend가 직접 프롬프트에 넣는 유일한 경로이며,
  이 계층 신설 전에는 계좌 평가금액·수익률·보유수량이 마스킹 없이 나갔다
  (`mcp-trading/tests/fixtures/balance_report.json` 픽스처로 실측·회귀 테스트함)
- `check_signal_significance`(뉴스/시그널 유의미성 판정) 경로

새 호출 경로가 provider별 구현(`_llm_openai_chat` 등)을 `llm_chat()` 밖에서 직접 부르면
`backend/tests/test_services.py::test_no_bypass_of_llm_chat_masking_layer`가 실패한다
(AST로 `backend/services.py`를 스캔해 호출부가 `llm_chat` 함수 본문 밖에 있으면 잡는다).

## 방식 — (a) 자리표시자 + 매핑 복원

```
보내는 프롬프트: "<ACCOUNT_1> 계좌, 삼성전자 <QTY_1>주, 평가금액 <AMOUNT_1>, 총자산 <AMOUNT_2>"
응답 수신 후   : <AMOUNT_1> -> 12,345,000원 로 역치환
```

매핑은 `llm_chat()` 호출마다 새로 만들어지는 지역 변수다. 모듈 전역에 두면
`asyncio.gather`로 병렬 호출되는 여러 `llm_chat()` 호출이 서로의 매핑을 덮어쓸 수
있어(스케줄러가 이런 구조로 호출한다), 요청 단위 격리를 지역 변수로 강제한다.

**한계**: 상대 비교(`AMOUNT_2 > AMOUNT_1`, 즉 "총자산이 평가금액보다 큰가")는 자리표시자만으로도
LLM이 판단할 수 있어 유지되지만, **절대 금액 기반 판단**("이 종목 비중이 1천만원으로
과도하다")은 원값이 프롬프트에 없으므로 LLM이 할 수 없다. 정밀한 절대 판단이 필요해지면
(b) 비율·구간 변환(예: "포트폴리오 대비 12%")을 별도 이슈로 검토해야 한다 — 변환 규칙·구간
경계 설계 비용이 #230 범위를 넘어 이번에는 채택하지 않았다.

**역치환 fail-open**: LLM이 자리표시자를 변형하거나(`<AMOUNT_9f2a1c_1>` → `<AMOUNT1>`) 존재하지
않는 자리표시자를 지어내거나(`<AMOUNT_9f2a1c_9>`) 다른 대화 턴의 자리표시자를 인용하면,
`unmask_pii()`는 예외를 던지지 않고 해당 부분을 `_FALLBACK_LABEL`의 짧은 명사(계좌/금액/수량)에
등장 순서 서수를 붙인 `"(이전 금액 1)"` 꼴로 치환한 뒤 경고 로그만 남긴다. 같은 자리표시자가
응답에 여러 번 나오면 같은 서수를 유지하고, 종류가 다르면 서수도 종류별로 따로 센다. 실측
(매핑 없이 역치환):

```
입력: "지난달 <AMOUNT_9f2a1c_1>에서 이번 달 <AMOUNT_9f2a1c_2>로 늘었고, 수량은 <QTY_9f2a1c_1>주였습니다."
출력: "지난달 (이전 금액 1)에서 이번 달 (이전 금액 2)로 늘었고, 수량은 (이전 수량 1)주였습니다."
```

서수가 없으면 한 응답에 인용된 서로 다른 자리표시자가 전부 같은 문자열로 접혀 "서로 다른
두 값이 같다"는 오정보가 생긴다 — 값을 지어내지 않으면서 토큰 노출만 막으려던 원래 목적과
정면으로 어긋난다. 서로 다른 자리표시자를 서로 다른 문구로 구분하는 것은 더 이상 알려진
한계가 아니라 이 fail-open 경로가 해소한 동작이다. 괄호는 조사 결합이 깨지는 것
(`"금액로"`, `"수량주입니다"`)을 막고 이 자리가 값이 아니라 참조임을 표시한다.
내부 토큰(`<AMOUNT_xxx_1>` 등)이 사용자 화면(텔레그램 메시지 등)에 그대로 노출되는 것을
막기 위함이다. 역치환 실패가 분석 결과 저장을 막지 않는다 — `_resolve_stock_code`의
실패 폴백, `stock_code.py`의 마스터 로드 fail-open과 같은 원칙이다.

이 경로는 **현재 턴에 PII가 없어 `mapping`이 비어도 발동한다.** 후속 질의("그럼 팔까?",
"왜?")는 정의상 PII가 없어 `mapping = {}` 이 되는데, NAT 대화 히스토리에서 이전 턴의
자리표시자(`<AMOUNT_xxx_1>`)가 응답에 인용될 수 있기 때문이다. `mapping`이 비어 있다는
이유로 조기 반환하면 이 자리표시자가 경고 로그 없이 그대로 사용자 화면에 노출된다.

## 정규식 채택 근거 (Presidio 미도입)

착수 시 실제 프롬프트 샘플(`_build_toolless_prompt`, `_build_nat_prompt`,
`generate_morning_briefing`이 조립하는 프롬프트, `mcp-trading/tests/fixtures/balance_report.json`
공유 픽스처)을 확인한 결과:

- 대상 3종은 모두 구조화된 표기 패턴이라 정규식으로 충분히 식별된다.
- **자유 입력 경로는 실재한다.** 다음 두 경로는 backend가 조립하지 않은 원문을 그대로
  LLM에 전달한다.
  - `backend/telegram_commands.py`의 `_handle_chat_fallback` — 명령어에
    매칭되지 않은 텔레그램 사용자 원문 텍스트를 그대로
    `llm_runner("nat", text, conversation_id=f"telegram:{chat_id}")`로 보낸다.
  - `backend/services.py`의 `check_signal_significance` — 외부 뉴스/시그널 원문
    (약 1000자)을 프롬프트에 삽입한다.
  - 이 경로들에는 인명·전화번호·주민등록번호·이메일이 들어올 수 있고, 현재
    recognizer 3종(계좌/금액/수량)은 이를 잡지 못한다. 다만 F-17이 정의한 마스킹
    대상은 이 3종뿐이며, 인명·연락처 등 NER이 필요한 대상은 이번 범위 밖이다
    (아래 "미적용 경로" 참고).
- `presidio-analyzer`는 spaCy NER 모델 다운로드가 Docker 이미지·CI 시간에 얹히는 비용이
  있어, 이 범위(계좌/금액/수량 3종)에서는 이점 없이 비용만 커진다.

근거는 이슈 #230 코멘트에도 남긴다.

## 미적용 경로 (한계로 명시)

이 계층은 **`llm_chat()`을 거치는 프롬프트만** 막는다. 아래 경로·대상은 이 계층 밖이며
후속 이슈에서 별도로 다루거나(1, 4) 구조적 한계·의도된 트레이드오프로 남긴다(2, 3, 5).

1. **NAT 내부 도구 호출 경로** — NAT 멀티에이전트가 자체적으로 MCP 도구(KIS 잔고 등)를
   호출해 만드는 프롬프트 조각은 backend가 보지 못하므로 마스킹할 수 없다. backend는
   `user_msg`만 NAT에 보내고, NAT 프로세스 내부에서 추가로 조회한 데이터는 그 안에서
   바로 OpenAI로 나간다. → **#231**에서 다룬다.
2. **Telegram 경유 계좌 정보(`/balance`, 주문 승인 메시지, 모닝 브리핑)** — LLM 호출이
   아니라 이 미들웨어의 사정거리 밖이다. `/balance`는 사용 목적 자체가 원값 표시이므로
   마스킹을 적용하면 명령의 존재 이유가 사라진다. **#232에서 비식별화 대상 제외로
   결정했다** — 확인 결과·감수하는 위험·대안을 버린 이유는 아래 "Telegram 경유 계좌
   정보 노출" 절에 적는다. 후속 이슈로 넘기는 항목이 아니라 여기서 닫힌 항목이다.
3. **정규식 커버리지의 구조적 한계** — `_ACCOUNT_RE`는 KIS_ACCOUNT_NO 형식(10자리,
   하이픈 유무 무관)만 다룬다. 다른 증권사 형식이나 표기 편차는 놓칠 수 있다.
4. **NER 대상(인명·연락처 등)** — "정규식 채택 근거" 절에서 확인했듯 자유 입력 경로
   (`_handle_chat_fallback`, `check_signal_significance`)가 실재하므로, 이 항목은
   "자유 입력이 없어서 불필요하다"가 아니라 **이번 범위(F-17의 계좌/금액/수량 3종) 밖이라
   다루지 않았다**는 뜻이다. 인명·전화번호·주민등록번호·이메일 마스킹이 필요해지면
   Presidio 등 NER 도입을 별도 이슈에서 검토해야 하는 열린 항목으로 남긴다.
5. **금액 표기 패치(`3a78eb4` 5차 · `246da88` 6차 · #330 8차 · #333 9차) 이후에도 남는
   금액 표기 간극과 알려진 과탐** — `_AMOUNT_UNIT_RE`는 5차 패치(`3a78eb4`)로 숫자-만/억
   사이 한글 수사(천/백/십) 갈래를, 6차 패치(`246da88`)로 **선행 아라비아 숫자가 아예
   없는 수사 단독 갈래**를, 8차 패치(#330)로 **`조`(兆) 단위와 마디 연쇄**를 추가로
   얻었다(마지막 것은 아래 첫 번째 항목에서 따로 다룬다). 그 결과 `"3천만원"`·`"1천5백만원"`·
   `"1천억원"`은 물론 `"천만원"`·`"삼천만원"`·`"오천만원"`·`"백만원"`·`"십만원"`·
   `"천억원"`·`"오천원"`·`"구십원"`처럼 수사만으로 표기된 금액(선행 숫자 없음)도
   이제 **값 전체가** 마스킹된다(실측 확인, 왕복 무손실). 이전까지는 이런 표기가
   전량 평문으로 나갔는데 이 사실이 이 문서 어디에도 기록돼 있지 않았다는 것이
   6차 리뷰 🟡1의 지적이었다 — 코드를 고쳤으므로 여기 반영한다.

   다만 다음 형태들은 패치 후에도 새어 나가거나, 뒤늦게 원인이 밝혀져 별도 패치로
   닫혔다(패치마다 동작이 바뀌었는지 재실측했다 — 첫 번째 항목은 #330으로 공백 없는 쪽이,
   두 번째 항목은 #333로 전부 해결됐고, 세 번째는 변화 없음). 이들과 원인이 다른 네 번째
   형태를 아래에 이어 별도로 기록한다:

   - **큰 단위 + 작은 단위가 이어지는 복합 표기 — 공백이 없는 쪽은 8차 패치(#330)로
     해결, 공백이 있는 쪽은 남는다** — `"3억 2천만원"`처럼 `억` 뒤에 **공백을 두고**
     별도 숫자로 시작하는 `천만원` 구간이 이어지면, 정규식은 `원`에 가장 가까운 뒤쪽
     구간만 매치하고 앞의 `"3억"`은 원문에 남는다(재실측: `"3억 2천만원"` →
     `"3억 <AMOUNT_1>"`, 매핑값 `"2천만원"`). `"1억 5,000만원"`도 같은 이유로
     `"1억 <AMOUNT_1>"`(매핑값 `"5,000만원"`)이 된다.

     공백 없이 붙는 표기는 8차 패치(#330)로 값 전체가 하나의 자리표시자가 된다.
     `_AMOUNT_UNIT_RE`의 첫 갈래를 "숫자+단위" 마디의 `{1,4}` 연쇄로 묶고 단위 갈래에
     `조`를 넣었다. 상한이 4인 이유는 두 가지가 겹쳐서다 — 단위는 조 > 억 > 만 순으로
     각각 많아야 한 번씩 나오므로 단위가 붙는 마디가 최대 3개이고(`"12조3456억7890만원"`),
     마디의 단위는 optional이라 **단위 없이 수사 런만으로 성립하는 꼬리 마디**가 맨 끝에
     하나 더 붙을 수 있다(`"1조5000억3000만5천원"`의 `"5천"`). 패치 전후 실측:

     ```
     "9조1800억원"          전: "9조<AMOUNT_1>"          후: "<AMOUNT_1>"
     "79조987억원"          전: "79조<AMOUNT_1>"         후: "<AMOUNT_1>"
     "1조5000억원"          전: "1조<AMOUNT_1>"          후: "<AMOUNT_1>"
     "10조원"·"500조원"     전: 전량 평문(단위를 모름)     후: "<AMOUNT_1>"
     "12조3456억7890만원"   전: "12조3456억<AMOUNT_1>"    후: "<AMOUNT_1>"
     "1조5000억3000만5천원" 전: "1조5000억3000만<AMOUNT_1>" 후: "<AMOUNT_1>"
     "3억2천만원"            전: "3억<AMOUNT_1>"          후: "<AMOUNT_1>"
     "9조 1800억원"         전: "9조 <AMOUNT_1>"         후: 동일 (공백은 여전히 간극)
     "3억 2천만원"           전: "3억 <AMOUNT_1>"         후: 동일 (공백은 여전히 간극)
     ```

     접두 13종 x 금액표현 50종 x 접미 8종 = 5200조합 차분 스윕에서 부분 마스킹이 전량
     마스킹으로 바뀌거나 새로 잡힌 것 1536건, 마스킹이 사라진 것 0건, 왕복 손실 0건,
     **스윕 범위 내** 새 과탐 0건이다. 스윕 밖에서 확인된 새 과탐 한 종류는 아래
     "알려진 과탐"에 적는다.

     남는 형태가 하나 더 있다. `조` 바로 앞이 숫자가 아닌 표기(`"수조5000억원"`·
     `"이조5000억원"`)는 첫 갈래가 선두 `\d+`를 요구해 `조` 앞에서 매치를 시작할 수 없어
     뒤 구간만 잡힌다(`"수조<AMOUNT_1>"`). 이때 lookbehind 문자 집합에 `조`를 넣으면
     뒤 구간마저 시작이 막혀 값 전체가 평문이 되므로 넣지 않았다 — 마디 연쇄에 상한이
     있어 시작 위치당 작업량이 상수이고, `조`를 넣어 얻을 성능 이득도 없다(실측: 8192자
     `'1조'` 반복 `mask_pii` 1.51 ms → 3.07 ms로 상수배 차이).

     **알려진 과탐 — 법조문 서수사 `제N조`.** `조`가 단위가 되면서, `"제1조"` 뒤에 `원`
     으로 시작하는 단어가 오면 `\s?원`이 그 첫 음절을 삼킨다. main에서는 불변이던
     형태가 #330에서 새로 마스킹된다:

     ```
     "제1조 원칙에 따라"  →  "제<AMOUNT_1>칙에 따라"
     "형법 제347조 원용"  →  "형법 제<AMOUNT_1>용"
     "제5조 원상회복"     →  "제<AMOUNT_1>상회복"
     ```

     감수한다. 왕복 무손실이라(85종 스윕 전건 확인) 역치환 후 사용자에게 보이는 값은
     그대로이고, `_AMOUNT_UNIT_RE` 주석이 이미 감수한 `"이백 원자재 가격"` →
     `"<AMOUNT_1>자재 가격"`과 같은 급·같은 원인의 과탐이다. lookbehind에 `제`를 넣는
     것은 해법이 아니다 — 바로 위에서 `조`에 대해 기각한 교환이 그대로 재현된다(실측:
     `"제1조5000억원"`이 `"제1조<AMOUNT_1>"`로 부분 마스킹되고 `"제1조원"`은 전량
     평문이 된다). 회귀 방지로 이 동작을 `test_masks_composite_big_unit_amount`의
     대조군에 한 줄로 고정해, 방향이 바뀌면(고치든 더 번지든) 테스트가 알려주게 했다.

     **아래 설명하는 부분 마스킹의 해악은 남은 형태들에 그대로 적용된다.** 전량
     마스킹이면 프롬프트에 크기 정보가 전혀 없고, 전량 미변경이면 원래 크기 그대로 남아
     채점 모델이 정확히 읽는다. 그런데 `"9조 <AMOUNT_1>"`처럼 부분 마스킹되면 `"9조"`
     라는 큰 단위 숫자는 평문으로 남고 바로 뒤에 실제 크기를 알 수 없는 불투명 토큰이
     붙는다 — 채점 모델이 이 조각을 "9조 원 규모"로 읽을 여지가 생기는 것이다(실제 값은
     9조 1800억원이라 자릿수 차이가 크다). 이는 6번 항목의 의도된 과탐(계좌번호 오분류)과
     성격이 다르다. 그쪽은 왕복 무손실이라 역치환 후 **사용자에게 보이는 최종 값**은
     훼손되지 않고 LLM 프롬프트 품질만 낮아지는 문제였다. 여기서도 매핑에 `"1800억원"`이
     정확히 남으므로 역치환 후 사용자 노출 값 자체는 정상이지만, 문제는 그게 아니라
     **마스킹 시점에 LLM이 실제로 읽는 값**이 실제 크기와 다른 크기로 왜곡된다는 점이다
     — 사용자에게 보이는 값이 아니라 모델이 읽는 값이 틀린 정보를 준다는 점에서 이
     문서가 이미 감수한 과탐들과는 다른 종류의 손실이다. 뉴스 본문의 금액이라 F-17의
     보호 대상(계좌/금액/수량 PII)은 아니므로 유출은 아니다. #330은 공백 없는 표기만
     고쳤고, 공백이 낀 표기는 알려진 간극으로 남긴다.

     이 부분 마스킹 문제와는 별개로, 뉴스처럼 F-17 보호 대상이 아닌 공개 시장 데이터에
     마스킹이 걸릴 때 유출 없이 채점 품질만 잃는 비용 자체는 더 넓은 주제다. 이 PR
     범위를 넘으므로 여기서는 다루지 않고, 필요해지면 별도 이슈로 검토한다.
   - **단위 뒤에 아라비아 숫자만 오는 표기(`"1만5000원"`) — 9차 패치(#333)로 해결** —
     원인이 위 항목과 다르다. 위쪽은 정규식이 표기를 몰라서 놓쳤지만, 이쪽은 **알면서
     적용 순서 때문에** 놓쳤다. `mask_pii`는 이미 치환된 텍스트를 다음 정규식에 넘기는데
     좁은 `_AMOUNT_WON_RE`(`원` 바로 앞 숫자)가 넓은 `_AMOUNT_UNIT_RE`보다 먼저 돌아,
     값의 꼬리 `"5000원"`만 자리표시자가 되고 앞자리 `"1만"`이 평문으로 남았다. 꼬리가
     한글 수사인 `"1만5천원"`은 8차 패치(#330)의 마디 연쇄가 이미 전량 마스킹해서,
     아라비아 숫자 꼬리만 남아 있었다.

     이 형태는 앞의 뉴스 본문 사례와 달리 **F-17 보호 대상이 실제로 새어 나가는**
     자리다. `"1만5000원"`·`"7만8000원"`은 주가·체결가 표기로 흔하고,
     `telegram_commands._handle_chat_fallback`이 텔레그램 사용자 원문을 가공 없이
     `llm_chat`으로 넘기므로 잔고·매수 문의에 그대로 실린다.

     고친 방법은 두 가지가 한 쌍이다. (a) `_AMOUNT_UNIT_RE`를 `_AMOUNT_WON_RE`보다
     **먼저** 적용하고, (b) 마디 연쇄 끝에 **단위 없는 순수 숫자 꼬리 마디**
     `(?:\d+(?:,\d{3})*(?:\.\d+)?)?`를 한 번 허용한다. 마디는 수사 런이나 단위 중
     하나를 요구하므로 `"5000"`은 마디가 될 수 없어, 순서만 바꾸면 값 전체가 계속 미매치가
     되고 뒤에 도는 `_AMOUNT_WON_RE`가 다시 꼬리만 가져간다(실측: 어느 한쪽만 되돌려도
     결과가 `"1만<AMOUNT_1>"`로 같다). 순서를 뒤집어도 안전한 이유는 `_AMOUNT_UNIT_RE`가
     마디에 수사나 단위를 요구해서 `_AMOUNT_WON_RE`만의 영역(`"1,234,567원"`·`"15000원"`
     처럼 단위 없는 표기)을 건드리지 않기 때문이다 — 겹치는 구간에서는 항상 단위 쪽이 더
     긴 값을 가져간다. 패치 전후 실측:

     ```
     "1만5000원"      전: "1만<AMOUNT_1>"   (매핑 "5000원")   후: "<AMOUNT_1>"
     "7만8000원"      전: "7만<AMOUNT_1>"   (매핑 "8000원")   후: "<AMOUNT_1>"
     "10만9900원"     전: "10만<AMOUNT_1>"  (매핑 "9900원")   후: "<AMOUNT_1>"
     "1천5000원"      전: "1천<AMOUNT_1>"                     후: "<AMOUNT_1>"
     "3억5000원"·"1조5000원"·"1만5,000원"·"1만5000.5원"도 같은 형태
     "1만 5000원"     전: "1만 <AMOUNT_1>"                    후: 동일 (공백은 여전히 간극)
     "1,234,567원"·"15000원"·"3천만원"·"1만원"·"1만5천원"·"9조1800억원"  전후 불변
     ```

     접두 13종 x 금액표현 65종 x 접미 8종 = 6506조합 차분 스윕에서 부분 마스킹이 전량
     마스킹으로 바뀐 것 1033건, **마스킹이 줄어든 것 0건, 왕복 손실 0건, 새로 잡힌
     비금액 표기 0건**이다. 성능도 상수배 안에 있다(8192자 `mask_pii` 실측, main → 현재:
     `'1조'` 반복 1.51 → 2.21 ms, `'1만5000'` 반복 3.83 → 5.87 ms — 회귀 테스트 상한
     0.5초의 1/85 수준).

     꼬리에 공백을 허용하지 않는 것은 의도다. `\s?`를 넣으면 `"제3조 5000원"`의
     `"5000"`까지 조 단위 값의 꼬리로 삼키므로, `조`/`억` 뒤에 공백을 두는 표기는 위
     항목의 알려진 간극으로 그대로 남긴다.

     **부수 효과 — 자리표시자 번호는 텍스트 등장 순서가 아니다.** `mask_pii`가 정규식별로
     한 번씩 훑으므로 번호는 훑는 순서를 따른다. 순서를 뒤집은 뒤 `"3000원 그리고
     1만5000원"`의 `<AMOUNT_1>`은 뒤에 있는 `"1만5000원"`이 된다. 이것은 다중 패스 설계에
     원래 있던 성질이고 이번 변경이 만든 것이 아니다 — main에서도 라벨 패스가 나중이라
     `"잔고 1234567 그리고 3천만원"`은 `<AMOUNT_2>`가 앞에 온다(main과 현재 동일). 번호는
     값의 동일성 표지일 뿐이고, 이 문서가 보존한다고 적은 능력(자리표시자끼리의 상대 비교)도
     번호의 크기가 아니라 서로 다른 토큰이라는 사실에 기대므로 영향받지 않는다. 회귀 방지:
     `test_masks_digit_tail_after_unit_marker`,
     `test_unit_and_bare_won_amounts_coexist_losslessly`.
   - **`원` 접미사가 전혀 없는 순수 `만`/`억` 표기** — `"3만"`, `"5억"`처럼 뒤에 `원`이
     붙지 않으면 세 정규식 중 어느 것도 매치하지 않아 **값 전체가** 원문에 남는다(재실측
     확인, 변화 없음). `_AMOUNT_UNIT_RE`는 `\s?원`으로 끝나야만 매치되므로 구조적으로
     이 형태를 다루지 않는다. 추가로 `"2,000 만원"`처럼 숫자와 단위 사이에 공백이 있는
     표기도 전량 마스킹되지 않는다(재실측 확인, 변화 없음) — `_AMOUNT_UNIT_RE`의 `\s?`는
     만/억과 원 사이에만 있고 숫자와 단위 사이 공백은 다루지 않는다.

   위 항목들에서 "남는다"고 적은 형태(단위 사이에 공백이 낀 복합 표기, `원` 접미사가
   없는 표기)는 고치지 않고 알려진 간극으로 남긴다.

   - **금액 직전 문자가 한글 수사일 때 매치 시작이 막히는 경우(앞의 형태들과 원인이
     다르다)** — 앞의 형태들은 `_AMOUNT_UNIT_RE`가 그 표기 자체를 애초에 모르는
     구조적 한계다. 이것은 다르다 — 정규식이 표기를 알면서도 **성능을 위해 의도적으로
     매치 시작 위치를 제한한 대가**로 생긴다.

     7차 리뷰 수정(`256fe26`)은 수사 단독 갈래(6차, `246da88`)가 들여온 O(n²)
     백트래킹을 없애려고 `_AMOUNT_UNIT_RE`의 lookbehind를 `(?<![\d,])`에서
     `(?<![\d,천백십일이삼사오육칠팔구])`로 넓혔다 — 콤마 뒤뿐 아니라 수사 12자
     뒤에서도 매치가 시작되지 못하게 막았다. lookbehind를 콤마만 막는 채로 뒀다면
     수사 런의 모든 위치에서 매치가 시작되고 각 시작이 런 전체를 소비했다가 `\s?원`에서
     실패해 되감으므로 O(n) 시작 × O(n) 되감기 = O(n²)가 된다. `mask_pii`는 async
     `llm_chat` 안의 동기 CPU 작업이라 그 시간만큼 이벤트 루프 전체가 멈추고,
     `_handle_chat_fallback`은 텔레그램 원문(최대 4096자)을 가공 없이 넘기므로 **봇에
     접근 가능한 사용자 누구나** 발동시킬 수 있었다(7차 리뷰 실측: 4096자 555.75ms →
     0.92ms, 8192자 3551.95ms → 4.16ms). 회귀 방지: `test_korean_numeral_run_does_not_blow_up`
     (값이 아니라 소요 시간을 단언하는 성능 회귀 테스트).

     8차 패치(#330)의 마디 연쇄는 이것과 **원인이 다른** 두 번째 폭발 경로를 들여왔다.
     연쇄가 생기면 `"1천1천1천…"` 같은 런을 "한 마디의 긴 수사 런"으로도 "여러 마디"로도
     쪼갤 수 있어 **한 번의 시작 위치**에서 분할 경우의 수가 런 길이에 대해 지수로
     늘어난다(입력 길이에 대한 O(n²)가 아니라 짧은 입력에서도 터진다 — 실측: 1024자
     `mask_pii` 5839.49ms). 마디 안의 수사 런을 소유 수량자로 확정해
     (`(?:[천백십]\d*)+` → `(?:[천백십]\d*)++`) 분할 자체를 없앴고(0.37ms), 매치 결과는
     바뀌지 않는다. 회귀 방지: `test_chained_unit_run_does_not_blow_up`.

     그 대가로 **금액 바로 앞 문자가 수사 12자 중 하나면** 그 앞 위치에서 시작할 수
     있는 매치가 없어져 값 전체가 원문에 남을 수 있다. 직접 실측(`256fe26`의
     `backend/pii_mask.py`를 스크립트로 임포트, 선행 문자 23종[수사 12자 전부 + 비수사
     조사·어미 11자] × 금액 표현 17종 = 391조합 전수 스윕)한 결과, **신규 과탐 0건,
     전량 미탐 126건**이었다(전달받은 수치는 132건이었으나 실측값은 126건이다 — 아래에
     이유를 적는다). 비수사 조사·어미 11자(`과은고에가를도만와다의`)는 391조합 중
     어느 것도 미탐을 만들지 않았다.

     126건은 고르게 퍼져 있지 않았다. 수사 12자 중 단위어 `천`/`백`/`십` 3자는 17개
     금액 표현 전부와 결합해도 미탐이 0건이었고, 나머지 숫자수사 `일이삼사오육칠팔구`
     (1~9) 9자는 각각 17개 중 14개에서 미탐이 나 9×14=126이 됐다. 남는 3개(각 숫자수사당)는
     뒤따르는 금액 표현이 `"천만원"`·`"백만원"`·`"십만원"`처럼 **숫자 없이 단위어로
     시작**하는 경우였는데, 이때는 선행 숫자수사가 그 단위어와 이어져 하나의 더 큰
     유효한 수 표기로 합쳐져 통째로 매치되므로(`"이"+"천만원"` → `"이천만원"` 전체가
     `<AMOUNT_1>`) 미탐이 아니라 다른 크기의 수로 정상 매치된 것이다. 전달받은 132건과
     126건의 차이는 이 예외 3개짜리 하위 패턴을 스윕용 금액 표현에 포함했는지 여부로
     보이며, 표본 구성 차이일 뿐 노출 조건 자체는 아래처럼 동일하다.

     노출 조건을 정확히 좁히면: **금액 바로 앞 문자가 숫자수사(`일이삼사오육칠팔구`,
     1~9)이고 그 뒤 금액 표현도 숫자(수사)로 시작할 때만** 값 전체가 새어 나간다.
     `천`/`백`/`십` 같은 단위어가 직전에 오는 경우, 조사·어미 등 비수사가 직전에 오는
     경우, 공백이 직전에 끼는 경우는 모두 정상 마스킹된다. 실측:

     ```
     "회사이천만원 대출 받았습니다"        -> "회사이천만원 대출 받았습니다"        (전량 평문)
     "월급이삼백만원인데 어디에 투자할까요"  -> "월급이삼백만원인데 어디에 투자할까요"  (전량 평문)
     "오구백만원"                        -> "오구백만원"                        (전량 평문)
     "3삼천만원"                         -> "3삼천만원"                         (전량 평문 —
                                                                              7차 이전엔 "3삼<AMOUNT_1>"
                                                                              부분매치였다)
     ```

     정상 마스킹되는 경계(실측 확인):

     ```
     "이천만원과 삼천만원"  -> "<AMOUNT_1>과 <AMOUNT_2>"   (직전 문자가 조사 '과'라 정상)
     "자산은오천만원"       -> "자산은<AMOUNT_1>"
     "잔고이천만원" / "연구비오백만원" / "생일선물로일백만원" -> 전부 정상 마스킹
     "월급이 삼백만원" / "회사 이천만원"                    -> 공백이 끼면 정상 마스킹
     ```

     **이것은 회귀가 아니라 6차에서 얻은 커버리지 일부를 성능과 맞바꾼 것이다.** 6차
     패치(`246da88`)가 처음으로 수사 단독 표기(선행 아라비아 숫자 없음)를 커버 범위에
     넣었고, 7차(`256fe26`)가 그중 "금액 직전 문자도 수사인" 부분집합만 O(n²) 방지를
     위해 다시 내줬다. 3방향 대조(`d9ac287`(6차 전) / `256fe26^`(6차 후·7차 전) /
     `256fe26`(현재))로 위 126건을 전부 재실측한 결과 **전부 `d9ac287`에서도 마스킹되지
     않았다** — main 대비 새로 생긴 유출이 아니라 6차 이후 잠깐 얻었던 커버리지를 7차가
     되돌린 것이고, 어느 조합도 `d9ac287`보다 나빠지지 않았다.

     소수의 금액이 마스킹을 벗어나는 품질 손실보다, 텔레그램 원문 4096자로 봇 접근자
     누구나 이벤트 루프를 수 초간 멈출 수 있는 O(n²) DoS를 막는 쪽을 우선했다 — 과소탐
     자체는 유출이라 이 문서의 다른 곳에서는 과탐보다 나쁘게 치지만, 여기서는 과소탐을
     완전히 없애는 대안(콤마만 막는 lookbehind)이 봇 서비스 자체를 정지시킬 수 있어
     더 나쁜 선택지였다. 이 트레이드오프는 이번 PR에서 그대로 유지하며, 고치려면
     수사 런 안에서도 O(n) 시간에 모든 시작 위치를 시도하지 않는 별도 매칭 전략이
     필요해 별도 이슈로 검토한다.

   **알려진 과탐(false positive) 1건** — 수사 단독 갈래가 추가되며 `"이백 원자재 가격"`
   → `"<AMOUNT_1>자재 가격"`(매핑값 `"이백 원"`)이 새로 생겼다(실측 확인). "이백"을
   수사로 인식해 뒤따르는 "원"과 묶은 결과다. 왕복은 무손실이라 사용자에게 최종
   노출되는 값은 원문과 같으므로 유출이 아니라 품질 문제이며, 6번 항목이 이미 감수한
   방향(과탐은 품질 저하, 과소탐은 유출이라 과탐을 택한다)과 같다.

6. **의도된 과탐(false positive)** — 라벨 없는 순수 10자리 숫자는 원리적으로 KIS
   계좌번호와 구분할 수 없다. 실측으로 재현된 예:

   ```
   "유닉스 타임스탬프 1723526400 기록" → "유닉스 타임스탬프 <ACCOUNT_1> 기록"
   "사업자등록번호 1234567890 확인"     → "사업자등록번호 <ACCOUNT_1> 확인"
   ```

   이 방향의 오류는 유출이 아니라 "LLM에 틀린 타입 문맥을 준다"는 품질 문제이고,
   반대 방향(과소탐 = 유출)보다 안전한 쪽이라 의도적으로 감수한다. (a) 방식은 왕복
   무손실이므로 역치환 후 사용자에게 보이는 값은 정확하다 — 과탐은 LLM이 보는
   프롬프트에만 영향을 주고, 최종 출력의 원값 표시를 훼손하지 않는다.

## NAT 경로에도 마스킹을 적용하는 이유

리뷰에서 "NAT은 자체 MCP로 잔고를 재조회해 OpenAI로 보내므로(#231) NAT 경로 마스킹은
유출을 막지 못하면서 NAT 컨텍스트만 훼손하는 게 아닌가"라는 지적이 있었다. NAT이
사실상 기본 provider라 영향이 크다고 판단해 별도로 조사했고, 결론은 다음과 같다.

**결정: NAT 경로에도 마스킹을 유지한다(심층 방어). 코드 변경 없음.**

근거:

- `_llm_nat_chat`(`backend/services.py`)은 NAT 서버로
  `messages=[{"role": "user", "content": user_msg}]` 1건만 보낸다. 이 `user_msg`에
  잔고 원본이 들어가는 경로는 `generate_morning_briefing`이 `_collect_morning_context`의
  `balance_text`를 직접 조립해 넣는 경우가 유일하다 — 그리고 그건 이 마스킹 계층의
  **의도된 적용 대상**이지 "훼손"이 아니다.
- 리뷰어가 우려한 손실(잔고 컨텍스트 상실)은 실제로는 NAT **서브에이전트가 자체
  조회한** 잔고에서 발생하는데, 그 경로는 `user_msg`와 무관하게 NAT 프로세스 내부에서
  OpenAI로 나간다(`finus_nat/configs/agents/trading_agent.yml`의
  `functions.trading_agent_react.tool_names`에 있는 `kis-trading-mcp-tool` → 같은
  함수의 `llm_name`인 `trading_openai_llm`). 즉 backend의 마스킹을 끄든 켜든 그
  경로는 달라지지 않는다 — 여기서 마스킹을 빼도 얻는 것이 없다.
- 반면 NAT 분기만 마스킹에서 제외하면 "`llm_chat()`을 거치는 모든 provider가 동일하게
  마스킹된다"는 불변식이 깨진다. 이 불변식은
  `backend/tests/test_services.py::test_no_bypass_of_llm_chat_masking_layer`가 AST로
  지키고 있고, provider별 특례가 생기면 향후 provider 추가 시 마스킹이 조용히 빠질
  위험이 커진다.
- 감수하는 비용: 모닝 브리핑에서 잔고 금액이 자리표시자로 나가므로 절대 금액 기반
  판단("이 종목 비중이 1천만원으로 과도하다")은 NAT이 할 수 없다. 이는 "방식" 절에
  이미 적힌 (a) 방식의 알려진 한계와 같은 것이며, 이를 감수한다.

정리하면 "미적용 경로" 1번 항목(#231, NAT 내부 도구 호출 경로)과는 상충하지 않는다.
NAT 내부에서 서브에이전트가 자체 조회해 만드는 프롬프트 조각은 여전히 #231의 몫이고,
backend가 `user_msg`로 직접 조립해 넣는 잔고 텍스트에 대한 마스킹은 그와 별개로
유지한다.

## Telegram 경유 계좌 정보 노출 — 한계로 명시 (#232)

`/balance`는 KIS 잔고 리포트에 값을 바꾸지 않는 `render()` 틀만 씌워 그대로 Telegram으로
보낸다(`backend/telegram_commands.py`의 `_handle_balance`). `render()`는 텔레그램으로 나가기
직전의 단일 통과 지점(`presentation.py`, #297)이지만 길이 예산이 없어 값을 지우거나 줄이지
않는다. 이 경로는 `llm_chat()`을 지나지 않으므로 위 마스킹 계층의 사정거리 밖이고,
마스킹을 걸면 명령의 존재 이유가 사라진다 — 금액을 보려고 쓰는 명령이기 때문이다.

**결정: Telegram 채널을 비식별화 대상에서 제외하고 한계로 기록한다. 코드 변경 없음.**

### 대상 — `/balance`만이 아니다

이슈 #232는 `/balance`와 주문 확인 메시지를 들었지만, 실제로 Telegram으로 나가는 계좌
정보는 네 갈래다. 일부만 예외로 적으면 나머지가 문서에서 빠진다.

| 경로 | 나가는 값 | 조립 지점 |
| --- | --- | --- |
| `/balance` (와 `balance:refresh` 버튼) | 보유 종목명·종목코드·보유수량·평균매입가·평가금액·평가손익·수익률 | `telegram_commands.py` `_handle_balance` → `mcp-trading/balance.js` `formatBalanceReport()` |
| 수동 주문 확인 메시지 (`/buy`·`/sell`) | 예상 주문금액·현재가·**예수금** | `telegram_commands.py` `_format_order_prompt` — `get_balance` 응답에서 예수금 줄을 골라 접두사만 떼고 그대로 붙인다 |
| 자율 제안 승인 메시지 | 예상 주문금액·현재가·**주문가능금액**·보유수량 | `order_assist.py` `format_approval_message` (`snapshot`은 `get_stock_quote`/`get_balance`/`get_orderable_cash` 병렬 조회에서 온다) |
| 모닝 브리핑 | LLM이 잔고를 근거로 쓴 문장 속 금액 | `scheduler.py` `morning_briefing_task` → `format_morning_briefing` |

주문 경로가 두 줄인 것은 표기 편의가 아니라 실제로 함수가 둘이기 때문이다. 수동 경로는
`get_balance`의 **예수금**을, 자율 제안 경로는 `get_orderable_cash`의 **주문가능금액**을
싣는다(#310). 한 줄로 합치면 한쪽을 고칠 때 다른 쪽이 문서에서 조용히 빠진다.

모닝 브리핑이 이 표에 들어가는 이유는 따로 있다. 이 프롬프트는 위 계층이 **마스킹하는**
대상이지만, `unmask_pii()`가 응답을 원값으로 되돌린 뒤 그 텍스트가 Telegram으로 나간다.
즉 이 계층은 LLM 제공자에게 가는 값을 막는 것이지 사용자에게 표시되는 값을 막는 것이
아니다 — Telegram 채널은 설계상 **원값 채널**이다.

### 확인 결과 — 수신자는 구조적으로 하나다

옵션 A("한계로 명시")를 택하려면 "수신자가 계좌 소유자 본인"이라는 전제가 코드로
성립해야 한다. #232의 확인 항목을 실제로 확인한 결과는 다음과 같다.

- **발신 대상은 설정값 하나로 고정된다.** `TelegramNotifier.chat_id`는
  `TELEGRAM_CHAT_ID`(`backend/config.py`)에서만 온다. `sendMessage`/`editMessageText`/
  `deleteMessage`/`sendChatAction` 네 호출 모두 페이로드의 `chat_id`로 `self.chat_id`를
  넣으며, 들어온 update의 chat id를 발신에 쓰는 호출부는 없다. 호출부가 chat_id를
  넘길 수 있는 인자 자체가 없어, 수신자를 바꾸려면 프로세스 환경변수를 바꿔야 한다.
- **수신 게이트가 두 진입점 모두에 있다.** `handle_update`는 `message.chat.id`가
  `notifier.chat_id`와 다르면 즉시 반환하고, `_handle_callback_query`도 같은 비교를
  한다. 제3자가 봇을 찾아 `/balance`를 보내도 KIS 조회까지 가지 않고 응답도 없다.
- **폴러의 실패 통지도 같은 필터를 지난다.** `_notify_updates_skipped`는
  `_update_chat_id(u) == self.notifier.chat_id`인 update만 문구에 넣는다. update 원문을
  통지에 싣는 유일한 자리라 여기가 새면 남의 메시지가 소유자 화면에 뜬다.
- **미설정 배포는 아무것도 보내지 않는다.** `enabled`가 토큰·chat_id의
  `is_placeholder_secret()` 검사로 정해지고, `send_text`는 `enabled`가 아니면 즉시
  `False`를 돌려준다.

이 결정의 전제는 위 네 가지가 전부 성립할 때만 유지되므로, 문서가 아니라 테스트가
지켜야 한다. 현재 상태는 이렇다.

- 발신 대상 고정 — `backend/tests/test_telegram_notifier.py`가 페이로드의 `chat_id`를
  직접 단언한다(이 PR 이전부터 있었다).
- 수신 게이트 — `/balance` 기준의 회귀 테스트가 없어
  `test_balance_ignores_updates_from_other_chats`를 추가했다. 명령과 버튼 두 진입점을
  한 테스트에서 함께 본다.
- 폴러 통지 필터 — 배치가 **전부** 남의 chat인 경우는
  `test_poller_skip_notice_skipped_for_other_chat`(#241)이 이미 덮고 있었다. 다만 필터를
  남긴 채 문구만 `updates` 전체로 만드는 변경은 그 테스트를 통과한다(실측). 그 경우
  남의 메시지 원문이 소유자 화면에 뜨므로, 소유자와 남의 chat이 섞인 배치를 보는
  `test_poller_skip_notice_omits_other_chat_labels_in_mixed_batch`를 추가했다.
- 미설정 시 무발신 — `enabled` 판정은 `test_telegram_notifier.py`가 덮는다.

### 그래도 남는 것 — 이 결정이 막지 못하는 것

"한계로 명시"는 위험이 없다는 뜻이 아니다. 요구사항 검토자가 짚을 지점을 미리 적는다.

1. **Telegram 사업자는 여전히 값을 본다.** 봇 API 메시지는 종단간 암호화가 아니며
   (비밀 대화는 봇에 적용되지 않는다), 대화를 지워도 서버 측 보존은 통제할 수 없다.
   #232가 문제로 든 "제3자 서버에 평문으로 남는다"는 사실 자체는 이 결정으로
   **해소되지 않는다 — 감수하는 것이다.** 위 확인 결과가 보이는 것은 "수신자 집합이
   소유자 하나"이지 "제3자 보관이 없다"가 아니다. 이 구분을 흐리면 문서가 실제보다
   강한 보장을 주장하게 된다.
2. **`TELEGRAM_CHAT_ID`가 개인 대화라는 보장은 코드에 없다.** 그룹·채널 id를 넣으면
   그 방의 모든 구성원이 잔고를 받는다. 코드는 문자열 비교만 하므로 개인/그룹을
   구분하지 않는다. 관례(개인은 양수, 그룹은 음수, 채널은 `-100` 접두)로 검증하는
   방법은 있지만, 본인이 소유한 비공개 그룹에 보내는 정당한 구성까지 막고 Telegram이
   id 체계를 바꾸면 조용히 오작동한다. 따라서 **운영 조건**으로 남긴다: 이 값은 소유자
   개인 대화 id여야 하며, 그룹 id를 넣는 순간 위 "수신자는 하나" 전제가 깨진다.
3. **실제 경계는 봇 토큰이다.** 토큰이 새면 공격자는 `getUpdates`로 소유자가 봇에
   보내는 메시지를 가로채고 봇을 사칭해 메시지를 보낼 수 있다. `chat_id` 게이트는 이
   경우 아무것도 막지 못한다(이미 보낸 잔고 메시지 자체가 `getUpdates`로 읽히지는
   않지만, 그것이 위안이 되지는 않는다). 이 결정의 전제는 "토큰이 지켜진다"이며,
   토큰이 로그로 새는 경로는 #257에서 이미 닫았다.

### 옵션 B·C를 택하지 않은 이유

- **옵션 B(기본 마스킹 + 옵트인)** — `/balance`를 쓸 때마다 확인 절차를 거치게 하는
  것인데, 되돌리는 조작이 원값 표시라 한 번이라도 옵트인하면 그 뒤로는 옵션 A와 같은
  상태가 된다. 노출 시점을 한 단계 뒤로 미룰 뿐 노출 자체는 그대로다.
- **옵션 C(요약만 보내고 상세는 프론트엔드로)** — #122로 `/api/v1/db/portfolio`가
  실데이터를 반환하기 시작해 대안 경로가 생긴 것은 맞다. 다만 `backend/main.py`는
  현재 CORS 미들웨어만 붙어 있고 **인증이 없다.** 이 노출면은 옵션 C가 새로 만드는
  것이 아니다 — `GET /api/v1/trading/balance`가 이미 `get_balance` 결과를 그대로
  `data.report`로 돌려주고 있어, `/balance`가 보내는 것과 같은 리포트가 이미 인증 없이
  나간다. 따라서 옵션 C의 실제 효과는 "노출면을 새로 연다"가 아니라 **Telegram 쪽
  노출을 줄이는 대신 이미 인증 없는 경로에 의존하게 된다**는 것이고, 그 교환이 순개선이라는
  근거가 없다. 이 경로에 인증이 생기면 다시 볼 값이 있다. (관련: "미적용 경로" 1번과
  마찬가지로 backend가 어떤 네트워크에 놓이는지가 전제다.)
