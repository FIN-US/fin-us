# 사람이 확인하는 장면 체크리스트

리허설 도구(`rehearse.py`)가 자동으로 돌리지 **않는** 장면이다. 텔레그램 화면·버튼·실제 전송이 영상의
본체라 사람이 직접 보내고 눈으로 확인한다. 녹화 전날(월·화 장중)에 한 번씩, 녹화 직전에 한 번 더 돈다.

## 공통 사전 조건

- [ ] Docker 스택이 떠 있다: `bash scripts/run_stack.sh`(backend·finus-nat·redis·frontend) + `kis-trade-mcp`(3300)
- [ ] `.env`의 `KIS_ORDER_ENV`가 모의(`demo`)이고 `KIS_REAL_ORDER_ENABLED`가 켜져 있지 않다 — S8은 **모의계좌에 실제 주문**을 낸다
- [ ] 녹화용 텔레그램 채팅이 `.env`의 `TELEGRAM_CHAT_ID`와 같은 채팅이다(봇은 그 채팅의 메시지만 처리한다)
- [ ] 화면에 토큰·chat id·계좌번호가 보이는 창(터미널, `.env` 편집기)을 닫았다
- [ ] 다른 세션이 같은 KIS 계좌로 측정·리허설을 돌리고 있지 않다(EGW00201 초당 한도)

---

## S1 — /start · /level 초보

**사전 조건**: 녹화용 채팅. 이전에 /level을 바꿨다면 상관없다(이 장면에서 다시 고른다).

**순서**
1. `/start` 보내기
2. 첫 메시지의 수준 버튼에서 **초보** 누르기(또는 `/level 초보` 입력)
3. 두 번째 메시지(투자 성향)는 녹화 대본대로 고르거나 건너뛴다

**확인할 화면 요소**
- [ ] 첫 메시지: "안녕하세요. 이 봇은 시세·공시·매매를 텔레그램에서 다룹니다." + "주식 투자 얼마나 익숙하세요?" + 수준 버튼
- [ ] 두 번째 메시지: 투자 성향 질문 + 안정형/공격형 버튼
- [ ] 초보를 고른 뒤: "설명 수준을 초보(으)로 바꿨습니다. 낯선 용어가 나오면 한 줄 설명을 붙여 드립니다."
- [ ] 이후 장면 답 끝에 `ℹ️ 용어: 설명` 줄이 붙는다(S3에서 확인)

**실패 시 대처**
- 응답이 없다 → `docker compose logs -f backend`에서 폴러 오류 확인. chat id가 다르면 아무 응답도 하지 않는다
- 버튼을 눌러도 바뀌지 않는다 → redis가 내려가 있다(`docker compose ps redis`). `/level 초보`를 텍스트로 다시 보낸다
- 투자 성향 버튼이 "투자 성향을 처리하지 못했습니다" → finus-nat이 메모리 없이 떠 있거나 내려가 있다. 성향은 건너뛰어도 S5 외 장면에는 영향이 없다

## S2 — 테스트 알림

실제 감시 알림과 같은 렌더링 함수로 만든 알림 한 통을 보낸다. 본문 "요약:" 줄 앞에 `[테스트]`가 항상 붙는다.

**사전 조건**: 레포 루트, `uv sync --project backend` 완료, S1에서 초보 선택(용어 각주가 붙는다).

**순서**
1. 먼저 출력만 해 본다(보내지 않음):
   `uv run --project backend python backend/scripts/send_test_telegram_alert.py`
2. 모양이 맞으면 실제 전송:
   `uv run --project backend python backend/scripts/send_test_telegram_alert.py --send`
3. 다른 예시가 필요하면(대본에 맞춰):
   `uv run --project backend python backend/scripts/send_test_telegram_alert.py --stock SK하이닉스 --source news --score 3 --signal-reason "HBM 대규모 공급 계약 보도" --decision BUY --urgency critical --send`

**확인할 화면 요소**
- [ ] 맨 위 배너 🚨(긴급도 high·critical) 또는 🔔
- [ ] "📊 영향도" 줄, 판단·이유·긴급도 한국어 필드
- [ ] "요약:" 줄 맨 앞 `[테스트]`
- [ ] 초보면 끝에 용어 각주

**실패 시 대처**
- 터미널에 전송 실패 → `.env`의 `TELEGRAM_BOT_TOKEN`·`TELEGRAM_CHAT_ID` 확인(값을 화면에 띄우지 않는다)
- `--send` 없이 돌렸다 → 기본이 dry-run이다. 출력만 되고 보내지 않는 것이 정상

## S7 — /advise (장중만)

**사전 조건**: **평일 09:00~15:30**(장 밖이면 주문 보조가 거부한다). S8과 같은 대기 주문 슬롯을 쓰므로
S8 전에 대기 주문이 없게 한다(`/cancel`).

**순서**
1. `/advise 삼성전자` 보내기
2. "⏳ 분석 중입니다..."가 떴다가 사라지고 제안 메시지가 오기를 기다린다(수십 초)
3. 영상에서 확정까지 보여줄 계획이 없으면 **❌ 취소**를 누른다(60초 지나면 자동 만료)

**확인할 화면 요소**
- [ ] 진행 메시지가 답이 오면 사라진다
- [ ] 제안이 승인된 경우: 매수/매도·수량·근거·검증 의견과 ✅ 확정 / ❌ 취소 버튼
- [ ] 거부된 경우: 거부 사유 문장(한도·검증 반대 등) — 버튼 없음. 이것도 정상 동작이다
- [ ] 확정은 60초 안에만 된다(/buy와 같은 확정 경로)

**실패 시 대처**
- "주문 불가: 현재 장 운영 시간이 아닙니다" → 장 시간 확인
- "이미 대기 중인 주문이 있습니다" → `/cancel` 후 다시
- "주문 보조 실패: …" → `docker compose logs -f finus-nat backend`. 제안·검증 에이전트 왕복 실패면 한 번 더 시도하고, 반복되면 이 장면을 빼고 S8로 간다

## S8 — 자연어 주문 1주 → 60초 확인 → 확정

**모의계좌에 실제 주문이 나간다.** 리허설 도구는 이 장면을 절대 자동으로 돌리지 않는다.

**사전 조건**: 평일 09:00~15:30, `KIS_ORDER_ENV` 모의, 대기 주문 없음(`/cancel`), 예수금이 1주 값보다 많다.

**순서**
1. `삼성전자 1주 매수` 보내기(자연어 주문은 "매수"/"매도"와 "N주"가 함께 있어야 주문으로 읽힌다)
2. 확인 메시지를 읽는다(화면에 잠시 머문다)
3. **60초 안에** ✅ 확정 누르기
4. "주문 완료: …" 메시지 확인 → 필요하면 `/balance`로 체결 반영 확인

**확인할 화면 요소**
- [ ] "삼성전자 매수 주문 확인" / 종목코드 005930 / 수량 1주 / 주문유형 시장가
- [ ] 예상 주문금액·현재가·예수금 줄
- [ ] ✅ 확정 / ❌ 취소 버튼, 만료 안내
- [ ] 확정 후 "주문 완료: …" 한 통

**실패 시 대처**
- "자연어 주문을 해석할 수 없습니다" → 문장에 "매수"와 "1주"가 함께 있는지 확인. 또는 `/buy 삼성전자 1`
- 60초를 넘겼다 → 확정 버튼이 만료된 주문으로 거부된다. 주문 문장을 다시 보낸다
- 확정 후 거절 메시지 → 메시지의 KIS 사유를 본다(장 시간·예수금). 모의계좌 서버 점검 시간이면 녹화를 미룬다
- 버튼이 반응하지 않는다 → 같은 채팅에 대기 주문이 둘이 아닌지, backend 로그의 콜백 처리 확인

## S13 — /visualize

**사전 조건**: `.env`의 `VISUALIZATION_URL`이 설정돼 있고 frontend(8080)가 떠 있다. 브라우저에서 그 주소가 열린다.

**순서**
1. `/visualize` 보내기
2. 답의 링크를 눌러 Unity 포트폴리오 시각화를 연다

**확인할 화면 요소**
- [ ] "Unity 포트폴리오 시각화:" + URL 한 줄
- [ ] 링크가 열리고 S8에서 산 종목이 보인다(체결 반영까지 몇 초 걸릴 수 있다)

**실패 시 대처**
- "시각화 URL이 설정되지 않았습니다" → `.env`에 `VISUALIZATION_URL`을 넣고 backend 재시작
- 링크가 안 열린다 → `docker compose ps frontend`, 녹화 PC에서 주소(포트 8080)가 닿는지 확인
- 화면이 비어 있다 → frontend 번들 버전 확인(`bash scripts/frontend_build_stamp.sh check`)
